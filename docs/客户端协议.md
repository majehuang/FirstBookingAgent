# 客户端消息协议 v1.1

> 冻结文档。任何变更走 [`开发计划.md`](../开发计划.md) §9 的流程。
> 线格式由 `WireFormatSnapshotTest` 锁定 —— 该测试红了就说明你正在做破坏性变更。

**版本**：`1.1`（`io.agentharness.protocol.Protocol.VERSION`）

---

## 1. 两个方向

| 方向 | 类型 | 说明 |
|---|---|---|
| 客户端 → 服务端 | `UserInstruction` | 用户消息与控制指令统一走这一个信封 |
| 服务端 → 客户端 | `ClientMessage` | 用户可见消息（**含用户自己发的**） |
| 服务端 → 客户端 | `ControlFrame` | 控制状态快照，独立通道 |

---

## 2. ClientMessage

```json
{
  "msgSeq": 1,
  "replyId": "r-1",
  "blockId": "u-i1",
  "role": "USER",
  "type": "TEXT",
  "fallbackText": "帮我订酒店",
  "payload": {},
  "createdAt": "2026-08-24T10:00:00Z"
}
```

| 字段 | 约束 |
|---|---|
| `msgSeq` | **每 session 独立、单调、无洞。**客户端的空窗判定完全依赖它（INV-10） |
| `replyId` | 所属 turn。用户消息用它所触发的那个 turn 的 id |
| `blockId` | 同一文本块的标识。相邻且同 `blockId` 的 `TEXT_DELTA` 可安全合并。最长 128 |
| `role` | `USER` / `ASSISTANT` / `SYSTEM` / `UNKNOWN` —— 谁说的 |
| `type` | 见 §3 —— 是什么内容 |
| `fallbackText` | **必填。**富消息不可为空，它是降级路径上唯一剩下的东西 |
| `payload` | 类型相关。卡片内容在生成时已冻结，重开会话所见即当时所见 |
| `createdAt` | ISO-8601 UTC。不用时间戳数字 —— 那会让各客户端的跨时区解析各显神通 |

`role` 与 `type` 是**正交**的两个维度。不把 `USER` 塞进 `type`，是因为用户将来也会发图片和语音，
那时需要的是 `(USER, IMAGE)` 而不是再造一个 `USER_IMAGE`。

## 3. MessageType

| 值 | 含义 | 富消息 |
|---|---|---|
| `TEXT` | 一条完整文本，不需要拼装 | |
| `TEXT_DELTA` | 文本增量 | |
| `TEXT_END` | 文本块结束，无正文 | |
| `TOOL_CALL` | 工具开始执行 | |
| `TOOL_RESULT` | 工具执行结束 | |
| `CARD` | 富消息卡片，内容已冻结 | ✓ |
| `IMAGE` | | ✓ |
| `AUDIO` | | ✓ |
| `ERROR` | 本轮出错，附用户可读原因 | |
| `SYSTEM` | 会话建立、被接管、被停止 | |
| `UNKNOWN` | **本客户端不认识的类型** | |

### 未知类型必须降级，不能报错

服务端会持续新增类型，而客户端的升级节奏不由服务端控制。因此：

- 反序列化遇到不认识的 `type` 或 `role`，**落到 `UNKNOWN`**，不抛异常
- 渲染 `UNKNOWN` 时按纯文本输出 `fallbackText`

没有这一条，服务端上线一个新类型就会让所有老客户端在反序列化那一刻整条流断掉——
`fallbackText` 的降级设计根本走不到。Java 实现靠 Jackson 的
`READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE` + `@JsonEnumDefaultValue`；
其它语言的客户端必须自行保证等价行为。

## 4. 能力协商

客户端建连时上报 `ClientCapabilities`：

```json
{ "protocolVersion": "1.1", "supportedTypes": ["TEXT", "TEXT_DELTA", "TEXT_END", "CARD"] }
```

- **不上报时按缺省能力处理：只保证文本。**保守的默认值意味着新客户端必须显式声明才能拿到卡片；
  反过来（默认全支持）会让任何一个老客户端在新类型上线时静默出问题
- 协商的语义是**服务端降级**而不是拒绝：不支持的类型在推送前压成 `TEXT`，
  正文取 `fallbackText`，`payload` 丢弃。内容不丢，只是失去结构
- 降级**不改变** `msgSeq`、`role`、`replyId` —— 打乱顺序会让空窗判定失效

---

## 5. 用户消息也落库，客户端不本地回显

```
输入 → 服务端落库（role=USER）→ 进流 → 客户端收到推送 → 才渲染
```

**这是强制要求，不是建议。**本地回显与流重放是两套顺序来源，只有一套受 `msgSeq` 约束。
去掉本地回显之后一个会话只剩一个 seq 空间：多端登录时各端顺序必然一致，
空窗判定不会被本地插入的行打乱，重开会话时自己问过的话也在历史里。

代价是多一个来回的感知延迟，客户端应当在这段时间给出"投递中"反馈。
**投递失败时必须把原文回显出来** —— 否则用户既看不到自己说了什么，也不知道要不要重发。

## 6. 投递与重试约定（INV-1）

服务端投递一条指令是**两条 Redis 命令**：

```
1. XADD {s<NNN>}:sess:<sid>:inbox <msg>     ← 必须先
2. XADD ready <sid>                          ← 后
```

顺序不可颠倒：反了的话摘牌脚本检查不到新消息，唤醒会丢。
两条都成功才返回 `202`，任一失败返回 `5xx`。

### 客户端的义务

> **超时或收到 5xx 时，客户端必须带同一个 `instructionId` 重试。**

这不是可选优化。单个全局 `ready` 与分片 `inbox` 必然不同槽，投递无法原子；
崩在两条命令之间时客户端收不到 `202`，那条消息就永久滞留在缝隙里——
除非客户端重试。**投递可靠性被有意挪到了客户端重试约定上。**

`instructionId` 由**客户端**生成，重试时保持不变。服务端生成没有意义。

### 服务端的幂等保证

- `(session_id, instruction_id)` 唯一索引，重复投递在**数据库层面**就写不进第二条
- **先查后分配**：先分配 `msgSeq` 再发现是重试，那个序号就烧掉了，序列里留下洞（违反 INV-10）
- 命中幂等时**不起第二轮**，回执带回原来的 `replyId` —— 否则客户端会去等一个不存在的 turn

### 回执

```json
{ "instructionId": "i-1", "replyId": "r-1", "msgSeq": 42 }
```

`msgSeq` 是**用户那条消息**的序号。

### 执行节点故障时的回复时延 SLA

收到 `202` 只表示指令已入队，**不表示已经有人在跑**。执行节点在中途挂掉时，
这一轮会由别的节点接管重跑，接管时延取决于节点是怎么没的：

| 情况 | 接管时延 | 说明 |
|---|---|---|
| 正常发布 / 滚动更新 | **≈ 0** | 节点主动交接，用户通常察觉不到 |
| 节点非预期死亡 | **≤ 90 秒** | 进程被强杀、OOM、宿主机失联、网络分区 |

**客户端不需要为此做任何事** —— 不要重试（`instructionId` 已经在队列里，重试只会命中幂等），
也不要提示用户重发。等待即可，接管后回复会照常从 SSE 流过来。

超过 90 秒仍无任何帧，才应当提示"服务繁忙"并允许用户手动重试。
把这个阈值设得更短会在每次节点故障时产生一批无谓的重试与用户困惑。

> 90 秒来自服务端的两个参数（滞留令牌判定 60 秒 + 回收扫描周期 30 秒）。
> 它是**上界**不是典型值；典型值在 50–90 秒之间。

## 7. 断线重连（客户端三规则）

服务端建连时从 outbox 窗口起点**全量重放**，不保存也不解析客户端位置。
因此重复必然发生，空窗也必然发生，这三条规则是唯一的收敛手段：

| 收到的 seq | 客户端动作 |
|---|---|
| ≤ 本地最大 | **丢弃**（重放重复） |
| == 本地最大 + 1 | **追加** |
| > 本地最大 + 1 | **清空渲染缓冲 → 拉取历史 → 重建 → 再接后续帧** |

> **"清空"后面必须跟着"拉取"。**只清空会让用户看到空白页。

第 3 条同时覆盖首次加载（本地最大 = 0，首帧 seq 必然远大于 1），
所以**首次打开与空窗恢复走同一条路径**，客户端不需要区分。

历史拉取：`GET /sessions/{sid}/messages?since=<本地最大seq>&limit=`，返回严格大于 `since` 的消息。
被重跑作废（`superseded`）的 `replyId` 由服务端过滤，客户端不需要知道这回事。
**用户自己的消息不会被作废** —— 重跑作废的是助手生成的内容。

## 8. UserInstruction

```json
{ "instructionId": "i-1", "kind": "MESSAGE", "priority": "QUEUED",
  "text": "帮我订酒店", "createdAt": "2026-08-24T10:00:00Z" }
```

```json
{ "instructionId": "i-2", "kind": "CONTROL", "priority": "IMMEDIATE",
  "targetReplyId": "r-1", "createdAt": "2026-08-24T10:00:00Z" }
```

| 字段 | 约束 |
|---|---|
| `kind` | `MESSAGE`（走 msg 游标）/ `CONTROL`（走 ctrl 游标） |
| `priority` | `QUEUED` / `IMMEDIATE`。打断走 `IMMEDIATE`，由持牌 pod 的 200ms 轮询扫出，绕开正常游标推进 |
| `targetReplyId` | `CONTROL` 必填。目标 turn 已不存在时服务端丢弃并推进游标 —— 防止误杀新 turn |

## 9. ControlFrame

```json
{ "turnActive": true, "inputAllowed": false, "activeReplyId": "r-1",
  "phase": "QUEUED", "stopping": false, "ctrlId": "1724-3" }
```

建连三步：

```
1. GET state                          → 完整快照 + ctrlId 水位
2. 下发快照
3. XREAD STREAMS ctrl-stream <ctrlId> → 开区间，只取水位之后的
```

`ctrlId` 必须与 `XADD` 在**同一个 Lua 脚本内**产生（INV-11）。
否则快照代表 T2 的状态、重放却从 T1 开始，旧帧覆盖新状态 —— **状态翻转**。

`phase` 取值：`IDLE` / `QUEUED` / `THINKING` / `CALLING_TOOL` / `WRITING` / `STOPPING` / `DONE` / `FAILED`。
