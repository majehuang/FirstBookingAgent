# 模块契约

模块之间没有 RPC、没有服务发现、没有共享内存 —— **接口就是那张 Redis key 表**。
这份文档是那张表的说明。

原先它是三条命令（`agent ingress` / `egress` / `dispatcher`），跑起来只会打印一段文字然后以退出码 3 退出。
一段文档伪装成命令，还占着一级命令表里的三个位置，所以搬到了这里。
键的**真实形态**改用 `/keys` 看 —— 它打的是当前会话的键（`{s169}:sess:s-1:inbox`），
而不是示例里的 `s-local`，可以直接贴进 `redis-cli`。

键名一律由 `KeyNamespace` 现算，`agent-keys` 之外任何地方出现键名字面量都会被
`KeyLiteralGuardTest` 拦下 —— 契约有了第二个版本时，表现是"消息投进去了但没人消费"：
Redis 不报错，日志没异常，只有用户觉得机器人不理他。

---

## 收消息（ingress）

交付阶段：P1（投递）/ P3（顺序与重试）/ P6（准入限流）
实现：`agent-comm/ingress`，会话进程通过它投递。独立进程形态待 HTTP 门面 ——
CLI 下它没有可服务的外部接口。

**职责**

- 鉴权与参数校验，`instructionId` 幂等键校验
- 投递：先 `XADD inbox`，后 `XADD ready`；两条都成功才回 202
- 准入限流：唤醒队列深度超阈值返回 503 + `Retry-After`

**读** `ready`（判队列深度）　**写** `inbox`、`ready`

**不变量**

- **INV-1** 两条 XADD 的顺序不可颠倒；未收到回执时客户端带同一 `instructionId` 重试
- **INV-9** 所有 key 走 `KeyNamespace`，分片数 256 永不修改

接 servlet 后它就是 `POST /sessions/{sid}/messages` 的处理器。

## 发消息（egress）

交付阶段：P1（消息流）/ P4（历史拉取）/ P5（控制流）
实现：`agent-comm/egress`，会话进程通过它读取两条流。

**职责**

- 消息流：建连后从 outbox 窗口起点**全量重放**，不解析任何位置参数
- 控制流：下发含 `ctrlId` 水位的快照，再从水位之后重放 ctrl-stream
- 历史拉取：`GET /sessions/{sid}/messages?since=&limit=`，直读消息表
- ctrl-stream 用 200ms 非阻塞轮询，**禁止 `XREAD BLOCK`**

**读** `outbox`、`ctrl-stream`、`state`、消息表（只读）　**写** 无

**不变量**

- **INV-12** 阻塞命令独占连接，Redis 连接数会随 SSE 连接数线性放大
- outbox **不用消费组**：那是扇出语义，用了之后多端登录各拿一半事件

接 servlet 后它就是两条 SSE 加一个历史拉取接口。

## 任务控制（dispatcher）

交付阶段：P1（简易消费循环）/ P3（消费组、心跳、回收、清理、上限）
实现：`agent-task/dispatch/ReadyDispatcher`，**与 worker 在同一个进程内**。
单独拆成进程要等多节点部署 —— 在那之前，把它列成一条命令等于承诺了一个不存在的部署形态。

**职责**

- `XREADGROUP` 消费唤醒队列，认领数量 = 空闲槽位数
- consumer 名 = pod 名，不加时间戳后缀
- 持牌期 `XCLAIM … JUSTID` 心跳，与 lease 续租同频 10s
- `XAUTOCLAIM` 回收：启动一次 + 每 30s，`MIN-IDLE-TIME 60000`，游标循环至 `0-0`
- 死 consumer 清理：先 `XAUTOCLAIM` 捞走工作，再对 `pending=0` 的 `DELCONSUMER`

**读** `ready`（消费组 `workers`）　**写** `lease`、`ready`（XACK）

**不变量**

- **INV-2b** Redis 没有 PEL 自动回队，不跑 `XAUTOCLAIM` 就是静默永久卡死
- **INV-2c** 没有心跳，`MIN-IDLE-TIME` 只能设成大于最长 turn，恢复时延变分钟级
- **INV-2d** 有 pending 时 `DELCONSUMER` 会连同条目一起销毁，工作无声蒸发
- 唤醒队列用 `MAXLEN ~ 100000`：`XTRIM` 不看 PEL，裁小了会在积压时静默丢工作

**consumer 名重名是这一层最隐蔽的坑。** 消费组按 consumer 名分配令牌，
重名的两个实例会互相抢消息、PEL 混在一起，症状是"消息有时没人处理"或"处理了两次"，
而现场看不出有第二个进程。所以内嵌 worker 的 consumer 名固定带 pid（`主机名-pid`），
独立 worker 本机多开时要显式 `--consumer` 区分。
