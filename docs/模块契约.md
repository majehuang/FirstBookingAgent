# 模块契约

模块之间没有 RPC、没有服务发现、没有共享内存 —— **接口就是那张 Redis key 表**。
这份文档是那张表的说明。

原先它是三条命令（`agent ingress` / `egress` / `dispatcher`），跑起来只会打印一段文字然后以退出码 3 退出。
一段文档伪装成命令，还占着一级命令表里的三个位置，所以搬到了这里。
键的**真实形态**改用 `/keys` 看 —— 它打的是当前会话的键（`{s169}:sess:s-1:inbox`），
而不是示例里的 `s-local`，可以直接贴进 `redis-cli`。

键名一律由 `KeyNamespace` 现算，`agent-keys` 之外任何地方出现键名字面量都会被
`KeyLiteralGuardTest` 拦下 —— 契约有了第二个版本时，表现是"消息投进去了但没人消费"：
Redis 不报错，日志没异常，只有用户觉得机器人不理他。

## 收消息（ingress）

交付阶段：P1（投递）/ P3（顺序与重试）/ P6（准入限流）
实现：`agent-comm/ingress`，会话进程通过它投递。独立进程形态待 HTTP 门面 ——
CLI 下它没有可服务的外部接口。

**职责**

- 鉴权与参数校验，`instructionId` 幂等键校验
- 投递：先 `XADD inbox`，后 `XADD ready`；两条都成功才回 202
- 准入限流：唤醒队列深度超阈值返回 503 + `Retry-After`

**读** `ready`（判队列深度）　**写** `inbox`、`ready`

**不变量**

- **INV-1** 两条 XADD 的顺序不可颠倒；未收到回执时客户端带同一 `instructionId` 重试
- **INV-9** 所有 key 走 `KeyNamespace`，分片数 256 永不修改

接 servlet 后它就是 `POST /sessions/{sid}/messages` 的处理器。

## 发消息（egress）

交付阶段：P1（消息流）/ P4（历史拉取）/ P5（控制流）
实现：`agent-comm/egress`，会话进程通过它读取两条流。

**职责**

- 消息流：建连后从 outbox 窗口起点**全量重放**，不解析任何位置参数
- 控制流：下发含 `ctrlId` 水位的快照，再从水位之后重放 ctrl-stream
- 历史拉取：`GET /sessions/{sid}/messages?since=&limit=`，直读消息表
- ctrl-stream 用 200ms 非阻塞轮询，**禁止 `XREAD BLOCK`**

**读** `outbox`、`ctrl-stream`、`state`、消息表（只读）　**写** 无

**不变量**

- **INV-12** 阻塞命令独占连接，Redis 连接数会随 SSE 连接数线性放大
- outbox **不用消费组**：那是扇出语义，用了之后多端登录各拿一半事件

接 servlet 后它就是两条 SSE 加一个历史拉取接口。

## 任务控制（dispatcher）

交付阶段：P1（简易消费循环）/ P3（消费组、心跳、回收、清理、上限）
实现：`agent-task/dispatch/ReadyDispatcher`，**与 worker 在同一个进程内**。
单独拆成进程要等多节点部署 —— 在那之前，把它列成一条命令等于承诺了一个不存在的部署形态。

**职责**

- `XREADGROUP` 消费唤醒队列，认领数量 = 空闲槽位数
- consumer 名 = pod 名，不加时间戳后缀
- 持牌期 `XCLAIM … JUSTID` 心跳，与 lease 续租同频 10s
- `XAUTOCLAIM` 回收：启动一次 + 每 30s，`MIN-IDLE-TIME 60000`，游标循环至 `0-0`
- 死 consumer 清理：先 `XAUTOCLAIM` 捞走工作，再对 `pending=0` 的 `DELCONSUMER`

**读** `ready`（消费组 `workers`）　**写** `lease`、`ready`（XACK）

**不变量**

- **INV-2b** Redis 没有 PEL 自动回队，不跑 `XAUTOCLAIM` 就是静默永久卡死
- **INV-2c** 没有心跳，`MIN-IDLE-TIME` 只能设成大于最长 turn，恢复时延变分钟级
- **INV-2d** 有 pending 时 `DELCONSUMER` 会连同条目一起销毁，工作无声蒸发
- 唤醒队列用 `MAXLEN ~ 100000`：`XTRIM` 不看 PEL，裁小了会在积压时静默丢工作

**consumer 名重名是这一层最隐蔽的坑。** 消费组按 consumer 名分配令牌，
重名的两个实例会互相抢消息、PEL 混在一起，症状是"消息有时没人处理"或"处理了两次"，
而现场看不出有第二个进程。所以内嵌 worker 的 consumer 名固定带 pid（`主机名-pid`），
独立 worker 本机多开时要显式 `--consumer` 区分。

## 持牌执行（worker）

交付阶段：P1（drain + outbox）/ P3（原子摘牌、心跳、续租失败中止）
实现：`agent-task/worker/SessionWorker`。

**顺序是这一层的全部内容**

```
抢 lease → 抽干 inbox → 摘牌（Lua，原子）→ 交差（XACK）
```

**交差的资格由摘牌结果决定，不由"处理完了"决定。** 摘牌有三种结局，
只有一种允许 `XACK`：

| 结局 | 含义 | 处置 |
|---|---|---|
| `UNLEASED` | 是持有者，inbox 也确实空了 | 摘牌成功，**可以交差** |
| `WORK_PENDING` | 是持有者，但游标之后还有条目 | 保住牌子，**回去继续 drain** |
| `NOT_HOLDER` | 牌子已过期或已被抢走 | 停手，**不交差**，令牌留给回收 |

`WORK_PENDING` 时重试摘牌是个很自然的写法，但那条新消息会被跳过。
必须回到 drain —— 收敛通常一到两轮，持续撞上说明投递长期快于处理，
那时候让出执行权（`WORK_PENDING` 结局，不交差）比死守更好。

**读** `inbox`、`cursor`、`lease`　**写** `lease`、`cursor`、消息表、`outbox`、`ctrl-stream`

### AgentState 并发语义（2026-08-28）

- `AgentStateStore` 只负责多 pod 共享状态持久化，生产使用 PostgreSQL，普通 LWW 写入即可。
- **同一 session 的 Worker 不双跑只由 lease（INV-3）保证。** 状态存储不是锁、选主器或 fencing token。
- `AgentStateStore` 不要求 `expectedVersion`、版本化读取、CAS 或冲突重试；缺少这些能力不构成 P3 阻断。
- 数据库即使保留 `version` 列，也只用于计数、迁移或排障，不能据此宣称状态写入具备 CAS。
- 任何绕过 lease 直接并发写 AgentState 的路径都违反模块契约；lease 丢失后由 `LeaseFence` 停止后续写入。

**持牌期间同时跑着三件事**，前两件由同一个 10s 定时器驱动、**必须同频**：

- lease 续租 —— 失败即落闸
- PEL 心跳（`XCLAIM … JUSTID`）—— 让令牌 idle 不增长
- 抽干与推理

两者分开会漂移，而漂移的后果是某一拍只续了 lease 没刷 idle（或反过来）：
要么牌子在手上但令牌被抢走，要么令牌在手上但牌子没了。

**续租失败 = 立即停止一切写入**（LSE-007/008/009）。这不是"出错了"，
是"我们已经不是这个 session 的合法写入者了"——很可能另一个 pod 已经接管并正在回复。
此后消息表、outbox、游标、ACK 一个都不能再动，连"这轮失败了"的 ERROR 消息都不写，
否则用户会在正常回复中间看到一句失败。

落闸由 `LeaseFence` 实现，**两道防线缺一不可**：取消（掐掉上游，模型不再生成）
+ 写入前校验（拦住 80ms 合批窗口里已经在途的那一批）。
只有取消会漏掉在途批次；只有校验则中止不是"立即"。

### 停机与崩溃走两条路

| | 触发 | 恢复方式 | 接管时延 |
|---|---|---|---|
| **优雅停机** | `SIGTERM` / `Ctrl+C` | 停止认领 → 等在飞跑完 → 剩下的主动交接 | **≈ 0** |
| **非预期死亡** | `SIGKILL` / OOM / 节点丢失 / 网络分区 / 超 TTL 长 GC | `XAUTOCLAIM` 回收 | **≤ 90 秒** |

**90 秒 = MIN-IDLE 60s + 回收周期 30s，不是 lease TTL 的 30 秒**——
lease 过期只让新持有者*能*抢到牌子，但没有唤醒令牌就没有人会去抢。
（2026-08-26 决议方案 A：放宽 SLA、参数不动，见开发规划 E 节 P3 修订。）

### 交接的四步，顺序全是有理由的

```
① 落闸       —— 停止一切写入，此后本 pod 不再是合法写入者
② 释放 lease —— 按值比对删除
③ 重投令牌   —— XADD 一个新的 ready
④ 交差旧令牌 —— XACK
```

**②③ 不能颠倒。** 先重投的话，抢到新令牌的 pod 会在牌子还没释放时 `tryAcquire`，
扑空之后判定为"有人正在处理"，把这次唤醒**交差掉** —— 唤醒就此消失，
那个 session 还是要等 90 秒。这是最容易写反的一步。

**③④ 也不能颠倒**：崩在 ③ 之后 ④ 之前，最坏是旧令牌稍后被回收、多一次唤醒，
而重复唤醒本就有幂等兜底；反过来先交差再重投，崩在中间就两个令牌都没有，session 彻底失联。

每一步崩溃的最坏结果都是**退化回 90 秒的回收路径**，而不是丢消息。

> ④ 看起来违反 INV-4（没摘牌就 ACK），实质不违反：INV-4 保护的是
> "通往这个 session 的路不能断"，而 ③ 已经铺了一条 idle 从零开始的新路，
> 旧令牌此刻是纯粹的重复品。

**停止认领与打断在飞是两件事。** 直接 dispose 订阅会把两件一起做掉 ——
正在生成回复的 turn 被拦腰砍断，用户看到说到一半停住，然后等 90 秒由别的 pod 从头重来。
所以有一个单独的 `draining` 开关只让 `pollOnce` 返回空。

## 兜底层级

### 要避免的只有一件事

单条消息滞留（投递崩在 inbox 与 ready 之间、令牌被 `XTRIM` 裁掉）**是可以接受的** ——
用户重发一条就好。重发之所以有效，是因为新消息带来新的唤醒令牌，
接管方抢到空闲的牌子后**会把之前滞留的那些一起抽干**。

真正致命的是**重发也没用**：

```
牌子一直被占着 → 每条新消息都被判成"有人在处理"→ 交差走人 → 会话永久失聪
```

所以兜底的目标不是"保住每一条消息"，而是**保证牌子最终一定会放开**。

### 牌子占着不放，只有两种成因

| 成因 | 兜底 | 时延 |
|---|---|---|
| 持有者**死了** | 停止续租 → `lease TTL` 自然过期 | ≤ 30s |
| 持有者**活着但这一轮卡死** | **持牌上限**：超过 15 分钟停止续租并落闸 | ≤ 15min + 30s |

第二种是唯一一个 TTL 救不了的：**续租一拍一拍地续着，牌子永不过期**，
而所有监控都正常 —— lease 在续、令牌在流转、没有异常。
只有持牌方自己知道"我已经拿着这个牌子多久了"，所以判定也只能放在它那里。

`maxLeaseHold` 的取值口径是**「没有任何正常 turn 会跑这么久」**，不是「turn 一般跑多久」。
15 分钟对多轮工具调用的长 turn 也留足余量；真触达它，那就是卡死，不是慢。

### 这一轮救不回来，也不打算救

停止续租之后，最多一个 TTL 牌子消失，**用户的下一条消息就能被正常处理**。
卡住的那一轮不写任何收尾消息 —— 它卡在哪儿我们并不知道。
用户看到的是这次没有回复，重发即可。

**这是刻意的取舍：目标是让会话恢复可用，不是让这一轮起死回生。**

### 其余三层

| 层 | 兜什么 | 时延 |
|---|---|---|
| 优雅停机交接 | 计划内重启 | ≈ 0 |
| `XAUTOCLAIM` 回收 | 令牌卡在死 consumer 的 PEL 里 | ≤ 90s |
| 客户端重试 | 投递崩在 inbox 与 ready 之间 | 取决于客户端 |

> **曾经考虑过、又撤掉的方案**：定期 `SCAN` 全部 inbox，找"有活儿但没人干"的 session 补发唤醒。
> 它解决的是"这一条消息滞留了"——恰好是上面说的、可以让用户重发的那类。
> 代价却不小：扫全键空间、要给 inbox 条目加属主字段才能重建令牌、
> 过载时大批 session 都"有活儿且无 lease"会触发全量重投把负载翻倍。
> **投入在错的那一半问题上。** 会话是否存活由牌子决定，不由 inbox 里有没有消息决定。

## 健康检查

P3 建起来的机制有个共同的坏毛病：**失效的时候是静默的**。

- `XAUTOCLAIM` 停跑 —— Redis 视角一切正常，没有任何错误日志，
  令牌就那么一直躺在 PEL 里（官方原话：*leave the messages pending forever*）
- 某一轮卡死 —— 续租一拍一拍地续着，牌子永不过期，
  此后该会话发什么都没人理，而 lease 在续、令牌在流转、监控全绿

这两种都没法靠"等报错"发现，只能**主动去看几个数**。

### 七个数，分两组

| 组 | 指标 | 说明 |
|---|---|---|
| 全局 | `lag` | 已投递但没人取走的令牌数 |
| 全局 | `PEL 深度` | 所有消费者名下 pending 总数（在飞 + 滞留） |
| 全局 | **`最老 pending idle`** | **`XAUTOCLAIM` 停跑的唯一信号** |
| 全局 | `consumer 数` | 含已死但还没清理的 |
| 本机 | `在飞 / 上限` | 满载时不再认领 |
| 本机 | **`最长持牌时长`** | **接近上限 = 有 turn 正在卡死** |

**全局与本机不能混着看。** "在飞 0 但 PEL 深度 50"单看本机像是闲着，
实际可能是别的 pod 忙着（正常），也可能是一堆令牌卡在死 pod 名下（不正常）。
分清楚才知道该查哪边。

### 三条告警规则

| 规则 | 阈值 | 含义 |
|---|---|---|
| 最老 pending idle | > 5 分钟 | 回收没在跑。稳态下不该有任何令牌 idle 到分钟级 |
| 最长持牌 | > 上限的 80% | 快被判定卡死了，趁现在看它卡在哪儿 |
| 槽位 | 满载 | 不再认领，积压留在 ready |

`concerns()` 返回的是**列表不是 boolean**：每条要查的地方完全不同，
压成"健康/不健康"之后运维拿到的信息还不如没有。

### 两个绕不开的实现约束

**读不到就报 `-1`，不要伪造 0。** `lag` 在 Redis 算不出来时会返回 nil
（消费组从 `$` 建起、Stream 被裁剪过等情况）。报 0 会让"队列很健康"
这个结论建立在一个根本没读到的数上 —— **指标上的假数比缺口更难查**。

**输出不走 slf4j。** `agent-cli` 绑的是 `slf4j-nop`，`log.warn` 在发布出去的二进制里
什么都不输出。健康检查恰恰是用来观测那些**本来就没有报错**的静默故障的，
所以它必须自己写 stream（与 `TurnLog` 同一个理由）。
独立 worker 走 stderr —— stdout 是一轮一行的可 diff 产物，告警掺进去就没法比对了。

> **健康时一个字都不打。** 心跳日志跑久了没人看，真出问题反而淹在里面。
> 代价是"检查还在跑吗"没法从输出确认，所以**检查循环自己挂掉时必须单独喊一声** ——
> 探针死了之后"没有告警"会被读成"一切正常"，那是最危险的误读。
