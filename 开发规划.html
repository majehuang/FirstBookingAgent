分布式 Agent 服务开发规划

HarnessAgent 单例负责推理，你的代码负责分布式调度与消息投递。 两者的边界只有一行 streamEvents()——边界越干净，多端、漂移、唤醒的问题就越不需要在 Agent 层解决。

A

已确定的项目约束

六项开工前决策已定。其中 D2 改变了存储分层，D5 与 D6 的组合产生了一条键命名的硬约束。

决定后果
D1企业内部，不做多租户userId 即员工 id，不折进 sessionId；准入层不做租户配额
D2用户可见消息单独存储；推理事件只做日志存储四层分离。消息表是真相源，不再从 AgentState 重建

D5阿里云 Redis，7.0，优先标准版键名保留 hash tag：标准版零成本，将来迁集群版不用改
D6用 Lua 保证原子摘牌可原子（同槽）；投递因 ready 不分片而退化为两条命令，见 C 节

待定workspace 文件系统方案

"不用沙箱"不等于"不用分布式文件系统"。 HarnessAgent 默认开启双层长期记忆， 会往 workspace 写 MEMORY.md 与 memory/YYYY-MM-DD.md。 多 pod 下用本地文件系统会让记忆按 pod 分叉。

A 关掉长期记忆，workspace 退化为只读种子目录——最简单，失去跨 session 记忆沉淀。
B RemoteFilesystemSpec + BaseStore（Redis），IsolationScope.USER——多 pod 共享记忆，不涉及沙箱，比沙箱轻得多。

企业内部助手场景推荐 B。此项在 P0 前定。

EVAL / EVALSHA 完全支持，原先的阻塞项解除。剩下的是选型决策。

1 · 引擎版本必须买 7.0
阿里云提供 7.0 / 6.0 / 5.0 / 4.0，没有 6.2 这一档，而 XAUTOCLAIM 与 MINID 都是 6.2 引入：

2 · 架构优先选标准版（主从），而非集群版
Lua 的槽约束只存在于集群架构：

标准版（主从）集群版
KEYS 数组强制否是（不能写死 key 名或用 Lua 变量拼 key）
同 slot 强制否是（否则 ERR … keys must be in same slot）

企业内部量级（几千并发连接、几百并发 turn）标准版绰绰有余，且省掉一整类槽约束问题。 {s07} hash tag 照样保留——标准版上无害，将来迁集群版不用改键名。

若最终仍选集群版：用直连模式，不要代理模式。直连下 Lettuce 原生处理槽路由， Lua 只受数据节点检查（宽松）；代理模式的额外语法检查只会带来惊喜。

摘牌（lease + inbox）✓{s07} 保证无合规
ctrl 状态（state + ctrl-stream）✓{s07} 保证无合规

投递侧已改为两条普通命令（因 ready 不分片）， Lua 只剩这两个同 session 脚本，风险面很小。

B

存储分层

四层，职责不重叠。D2 确定后，消息表成为真相源，outbox 退化为实时推送与短期续传的缓存。

存储内容保留角色
消息表（DB）用户可见消息，卡片内容已冻结长期真相源：历史拉取、超窗重放
outbox（Stream）同一批消息的打包副本5–10 分钟实时推送、跨 pod 扇出、断线重放
事件日志（冷存储）全量 AgentEvent按合规要求排查与分析，异步写，不阻塞 turn
AgentState（Redis）模型上下文随 session框架自管，与客户端消息无关

写入顺序固定：消息表 → outbox →（异步）事件日志。
反序会导致"用户看到了、刷新后消失"——持久化必须先于可见。

消息序号与重连协议

每 session 一个单调递增且无洞的 msgSeq，同时充当消息表主键的一部分与 SSE 的 id。 不能用 DB 全局自增主键——多 session 交错会让每个 session 看到的序号是断的。

客户端连接时不带任何位置参数，服务端把 outbox 窗口内的消息全量重放。 去重与空窗判定由客户端完成——这是正确性的一部分，不是可选优化：

收到的 seq客户端动作
≤ 本地最大 seq丢弃（重放重复）
== 本地最大 + 1追加
> 本地最大 + 1清空渲染缓冲 → 拉取历史 → 重建 → 再接后续帧

第 3 条同时覆盖首次加载（本地最大 = 0，首帧 seq 必然远大于 1）—— 首次打开与空窗恢复走同一条路径，客户端不需要区分。

注意 · "清空"后面必须跟着"拉取"：只清空会让用户看到空白页。完整动作是 清空缓冲 → GET /sessions/{sid}/messages?since=… → 用结果重建。

洞是可自愈的：若落库成功但 XADD 失败，stream 里会缺一个 seq， 客户端判定为空窗后走拉取，消息表里那条记录还在，能补上。前提是 INV-5 的"先落库后 XADD"。

控制通道的重连协议

控制状态是 LWW 快照，但每次变更都追加一帧到 ctrl-stream—— 这样一闪而过的瞬时信号（stopping、supersededReplyId）不会被轮询窗口漏掉。

快照与流位置必须严格对齐，否则会状态翻转：快照代表 T2 的状态，重放却从 T1 开始，旧帧覆盖新状态。 对齐方式是把水位写进状态自身，且与 XADD 在同一个 Lua 脚本内产生。 

-- KEYS[1] = {s07}:sess:<sid>:state
-- KEYS[2] = {s07}:sess:<sid>:ctrl-stream      ← 同槽，靠 {s07} 保证
-- ARGV[1] = JSON patch   ARGV[2] = ttl 秒
local cur = redis.call('GET', KEYS[1])
local obj = cur and cjson.decode(cur) or {}
for k, v in pairs(cjson.decode(ARGV[1])) do
    if v == cjson.null then obj[k] = nil else obj[k] = v end
end

local id = redis.call('XADD', KEYS[2], 'MAXLEN', '~', 200, '*', 'f', cjson.encode(obj))

obj.ctrlId = id                                  -- ★ 水位写回状态自身
redis.call('SET',    KEYS[1], cjson.encode(obj), 'EX', tonumber(ARGV[2]))
redis.call('EXPIRE', KEYS[2], tonumber(ARGV[2]))
return cjson.encode(obj)

建连三步：

1. GET state                          → 完整帧 + ctrlId 水位
2. 下发快照
3. XREAD STREAMS ctrl-stream <ctrlId>  → 开区间，只拿水位之后的

因为 ctrlId 与 XADD 原子产生， 快照与流位置严格对应——既不漏也不重，翻转在结构上被排除。

待实测 · XADD 用 * 生成 ID 属于非确定性命令。Redis 5+ 走效果复制没问题， 但云产品若有额外限制需实测。

C

Redis 键命名规范

在 P0 一次定死。分片数 256 永不修改——修改等于数据迁移。

s07 = hash(sessionId) % 256      ← hash tag，让同一 session 的几个 key 落在同一个槽
键类型用途保留
{s07}:sess:<sid>:inboxStream有序指令队列（消息 + 控制）按条数或时间裁剪
{s07}:sess:<sid>:outboxStream客户端消息批5–10 分钟，受 turnStartId 保护
{s07}:sess:<sid>:cursorHashmsg / ctrl 两个游标≥ inbox 保留期
{s07}:sess:<sid>:leaseString执行权，值每次抢占唯一PX 30000，每 10s 续
{s07}:sess:<sid>:stateString控制状态快照，含 ctrlId 水位随 session
{s07}:sess:<sid>:ctrl-streamStream控制状态帧序列，每次变更追加一帧MAXLEN ~ 200 + TTL
ready（不分片）Stream + 消费组全局唤醒令牌队列，XREADGROUP 抢占MAXLEN ~ 100000

分片的作用：让同一 session 的几个 key 同槽，使摘牌脚本可以原子执行。

摘牌脚本（原子，同槽）： 校验 {s07}:sess:abc:lease  +  检查 {s07}:sess:abc:inbox  →  DEL lease

ready 刻意不分片——换来的是每个 pod 只监听一条 stream、只占一条阻塞连接。 代价是投递侧无法原子（ready 与 inbox 必然不同槽），退化为两条命令，顺序不可颠倒： 

1. XADD {s07}:sess:abc:inbox <msg>      ← 必须先
2. XADD ready <sid>                     ← 后
两条都成功才返回 202；任一失败返回 5xx

崩在两条之间时客户端收不到 202，会带同一 instructionId 重试，两条重新写入，重复由幂等检查吃掉。 这把投递可靠性挪到了客户端重试约定上，必须写进协议文档。

陷阱 · cursor 的 TTL 短于 inbox 保留期时，空闲久的 session 被唤醒会从头重放全部历史指令。 最省事的做法是 cursor 不设 TTL，随 session 一起显式清理。

模块职责与边界

模块职责碰哪些存储扩容依据
收消息模块鉴权、校验、写 inbox+ready、准入限流Redis（只写 inbox / ready）请求 QPS
发消息模块两条 SSE 的建连与推送、历史拉取Redis（只读 outbox / ctrl-stream / state）+ 消息表（只读）并发 SSE 连接数
任务控制模块ready 消费、consumer 生命周期、回收清理、在飞上限Redis（ready 消费组 + lease）每 pod 一个实例
Worker 模块session 生命周期、双游标、事件分流与落库Redis（全部）+ 消息表（写）+ 冷存储（写）并发 turn 数
工具模块业务查询、富消息表达（tool + middleware 成对）业务库 / 业务接口随任务层

模块间契约就是键命名规范

模块之间没有 RPC、没有服务发现、没有共享内存——接口就是 C 节那张 key 表。 新增模块只需要知道读写哪些 key，不需要认识任何其他模块。

守住 · 任何模块间的直接调用都是设计外的。一旦出现，独立部署和独立扩容就没了。

是否拆分部署

合并部署（一个服务）拆分部署（通信层 / 任务层）
适用P1–P3 开发期、小规模生产环境
扩容一起扩，按较大的那个维度各自按自己的维度扩
隔离LLM 慢会影响 SSE 推送线程互不影响
运维一套两套

拆分的实际价值在于两个维度不成比例：1000 个用户挂着 SSE 连接，同时可能只有 50 个在等回复。 合并部署时你得按 1000 扩容，任务层跟着白扩。

建议 P1–P4 合并部署，P5 之后视连接规模决定是否拆。 因为模块间只经由 Redis 通信，拆分不需要改任何代码，只是打不同的启动参数。

E

六个阶段

严格依赖有序：每一阶段都建立在前一阶段的验收之上。规模按 2–3 人小组的人周估算。

P01 人周

地基

单机跑通 HarnessAgent，把所有"上线后改不了"的约定锁死。

交付
  • 向云厂商确认 Redis 三项（版本 / Cluster / Lua 开放）——最先做
  • 确定 workspace 文件系统方案（关记忆 或 RemoteFilesystemSpec）
  • HarnessAgent 单例 Bean + RedisDistributedStore（应用启动时构建一次）
  • 客户端全线统一 Lettuce reactive
  • 键命名规范落地（含 256 分片 hash tag）
  • 消息表 DDL + msgSeq 分配方案
  • 客户端消息协议 v1：type 枚举、fallbackText 必填、能力协商
验收

单进程完成一次多轮对话；进程重启后，相同 (userId, sessionId) 能接着聊。 恢复是框架自动的——不需要为此写任何代码。

P12–3 人周

单节点闭环

POST → inbox → drain → agent → 消息表 → outbox → SSE 全链路打通，先不管多节点。

交付
  • POST /sessions/{sid}/messages → 202 {replyId, msgSeq}，不等 agent 执行
  • inbox（Stream）+ ready（全局 Stream + 消费组）+ lease + drain 循环（此阶段允许非原子摘牌）
  • OutboxWriter：bufferTimeout(64, 80ms) → 合并相邻同 blockId delta → 先落消息表 → 后 XADD
  • GET /sessions/{sid}/events 单条 SSE，id = msgSeq；连接不带位置参数，全量重放窗口内消息
  • 事件日志异步落冷存储（旁路，失败不影响 turn）
明确不做

多节点、断线降级、控制通道、卡片——全部留给后面阶段。

验收

单用户完整对话，文本流式无卡顿（更新频率 10–20 次/秒）；刷新页面能续上。

P22 人周

消息渲染

文本以外的消息类型端到端：卡片、图片、语音，以及后续扩展的接入流程。

交付
  • ClientMessage 协议 + render(toolName, payload) 纯函数
  • MessageAdapter：per-reply reducer，只累积文本，AgentEnd 时销毁
  • 表达型工具（send_hotel_cards 等），返回值带 shown 摘要供模型续接
  • onActing middleware：从 ActingInput.toolCalls() 取入参 → 服务端补全 → withMetadataEntry
  • 补全后的完整卡片写入消息表（冻结），永不重查
  • 卡片 UI 标注数据时间（"数据截至 …"），避免用户误读为实时价
验收

酒店推荐场景：一段推荐理由 + 一个三张卡片的消息组件 + 一句追问，按正确顺序到达。 关闭页面重开，卡片内容与首次生成时完全一致。

风险 · INV-7 —— 补全若走阻塞 JDBC，必须显式 subscribeOn(boundedElastic)，否则拖垮整个 pod 的事件循环。

P33–4 人周

多节点正确性

任意 pod 处理任意 session，pod 崩溃自动接管。整个规划里最难、最值得投入测试的一阶段。

交付
  • 投递：两条命令，XADD inbox 先、XADD ready 后；两条都成功才返回 202
  • 摘牌 Lua（同槽，可原子）：校验持有 → 确认 inbox 已抽干 → DEL lease
    • 启动时 SCRIPT LOAD，运行期 EVALSHA；单独成文件并注释为何必须原子
    • 用 testcontainers 起真 Redis 写单测
  • 消费组初始化：XGROUP CREATE ready workers 0 MKSTREAM，吞掉 BUSYGROUP
  • consumer 名 = pod 名（不加时间戳后缀——同时存活的 pod 本就不会重名，加后缀只会让死 consumer 堆积更快）
  • 持牌期心跳：与 lease 续租同频（10s）XCLAIM ready workers <自己> 0 <令牌ID> JUSTID， 重置 idle 计时且不增加投递计数。没有它，MIN-IDLE-TIME 只能设成大于最长 turn，恢复时延变成分钟级
  • XAUTOCLAIM 回收：pod 启动时跑一次 + 每 30s 周期跑
    • MIN-IDLE-TIME 60000，不能填 0（会抢走存活 pod 的令牌）
    • 循环调用直到返回游标为 0-0
    • 任意 pod 都跑，幂等，不选主
  • 死 consumer 清理：定期 XINFO CONSUMERS，对 idle > 1h 且 pending = 0 的执行 XGROUP DELCONSUMER
    • 顺序必须是「先 XAUTOCLAIM 捞走工作，后 DELCONSUMER 清元数据」
    • DELCONSUMER 会连同该消费者的 pending 记录一并销毁，那些条目既不在 PEL 也不是新条目， 从消费组视角彻底消失，无任何报错。pending = 0 不是优化，是安全前提
  • ready 用 MAXLEN ~ 100000——XTRIM 不看 PEL，裁小了会在积压时静默丢工作
  • 顺序固定：抽干 → 摘牌（Lua）→ XACK 令牌。先 ACK 再摘牌，崩在中间就没有任何线索
  • lease 抢占（SET NX PX，值每次唯一）+ 每 10s 续租 + 续租失败立即中止 turn 并停止写 outbox
  • 认领数量 = 空闲槽位数（认领即持有，多领等于制造饥饿）
  • 两个游标 + instructionId 幂等（对照上下文最后一条 USER 消息去重）
  • AgentStateStore 走支持 CAS 的后端，冲突失败重试
验收

混沌测试：持续对话下随机 kill pod、注入 Redis 抖动、模拟长 GC。要求 无消息丢失、无重复回复、无 session 永久卡死。优雅停机时用户无感知，硬杀时恢复时延 ≈ lease TTL。

风险 · INV-1 INV-2 INV-3 INV-4 —— 四条不变量全部是"写错了平时看不出、压力下才丢数据"的类型。 若云厂商禁用 Lua，本阶段改为兜底扫描方案（另：XREADGROUP 自 Redis 8.4 起支持 CLAIM <min-idle-time>，可把认领折进正常读取循环，届时能删掉独立的回收任务；6.2 用不上）（每 60s 扫"inbox 非空且无 lease"的 session 重新入队），最坏延迟约 90 秒。

P41 人周

断线重连与一致性

客户端在任何时刻断开重连，都能无重复、无缺失地接上。

因两项决定而简化

消息单独存储 + 全量重放叠加后，服务端的续传定位逻辑整块删除，本阶段从 2 人周降为 1 人周。

服务端交付（很薄）
  • SSE 建连后从 outbox 窗口起点全量重放，不解析任何客户端位置参数
  • turnStartId 保护：turn 进行中不允许裁剪 outbox
  • 历史拉取接口：GET /sessions/{sid}/messages?since=<msgSeq>&limit=，直读消息表
  • outbox 保留窗口收敛到 5–10 分钟（长期历史由消息表兜底）
  • 消息表加 superseded 列；拉取接口过滤掉被重跑作废的 replyId
客户端交付（正确性在这一侧）
  • 三条去重 / 空窗规则（见 B 节），需写成可测试的单元
  • 空窗时：清空缓冲 → 拉历史 → 重建 → 接后续帧
验收

turn 进行中反复断网重连，最终文本与不断网时逐字节相同；离线超过 outbox 保留窗口后重连， 能从消息表无缝续上，不出现空洞也不出现重复；首次打开会话与空窗恢复走的是同一条代码路径。

P52 人周

控制通道与打断

停止按钮 1 秒内生效，且崩溃重跑后不会误杀新 turn。

交付
  • control SSE 建连三步：下发完整快照（含 ctrlId）→ 从水位之后重放 ctrl-stream → 接后续帧
  • 状态变更走 Lua 脚本：合并 patch → XADD 到 ctrl-stream → 水位写回 state，三步原子
  • ctrl-stream 读取用非阻塞轮询（200ms）。每条 SSE 各自轮询即可——Lettuce 对非阻塞命令多路复用，不占连接。 禁止 XREAD BLOCK：阻塞命令必须独占连接，Redis 连接数会随 SSE 连接数线性放大。 连接数上千后再改 pod 级批量读，收益是往返次数与多端去重
  • ctrl-stream MAXLEN ~ 200 + TTL，与 state key 同生命周期
  • 状态帧字段：turnActive / inputAllowed / activeReplyId / phase / stopping / supersededReplyId
  • 统一 inbox 的指令分类：IMMEDIATE（打断）/ QUEUED（HITL 恢复结果、状态类）
  • pod 级轮询器（同一个 200ms 循环）扫本 pod 持牌 session 的 inbox，只捞 IMMEDIATE
  • 跨节点中断复用 inbox，不额外开 pub/sub：任意 pod 把 cancel 写入 inbox（IMMEDIATE + targetReplyId）， 持牌 pod 轮询扫到后调 agent.interrupt()
  • targetReplyId 作用域校验：目标 turn 已不存在则丢弃并推进游标
  • turn 重跑清理：接管方写 supersededReplyId，并把消息表中该 replyId 的行标记 superseded
验收

turn 进行中点停止，1 秒内 UI 进入"正在停止"，已生成部分保留； kill 执行节点后重跑，旧的停止指令不会打断新 turn； 反复断开重连 control SSE，状态不出现翻转（先看到 turnActive:false 又变回 true）。

交付

F

不变量清单

跨所有阶段必须成立。每一条都是"违反后平时看不出、压力或故障下才暴露"的类型——建议写进 code review checklist。

编号约束违反后果
INV-1 投递顺序必须 inbox 先、ready 后；两条都成功才返回 202，客户端在超时/5xx 时用同一 instructionId 重试 顺序颠倒 → 摘牌脚本检查不到新消息 → 丢唤醒；不重试 → 崩溃缝隙里的消息永久滞留
INV-2 摘牌必须与"确认 inbox 已空"在同一 Lua 脚本内（同槽：lease + inbox） 释放瞬间进来的消息无人处理
INV-2b XAUTOCLAIM 是必交付项：启动跑一次 + 每 30s 周期，MIN-IDLE-TIME 不为 0，循环游标至 0-0 Redis 没有 PEL 自动回队机制（官方原话 leave the messages pending forever）。不跑就是静默永久卡死，且 Redis 视角一切正常
INV-2d DELCONSUMER 只能在 pending = 0 时执行，且必须排在 XAUTOCLAIM 之后 有 pending 时删除消费者会连同那些条目一起销毁，工作无声蒸发
INV-2c 持牌期间用 XCLAIM … JUSTID 给自己的令牌续 idle 长 turn 被误回收产生 churn；或被迫把 MIN-IDLE-TIME 设成分钟级
INV-3 lease 值每次抢占唯一（非 pod 名），释放用值比对删除 同 pod 的另一个 worker 误摘他人的牌子 → 双跑
INV-4 顺序固定：抽干 → 摘牌 → 交差；续租任务在 doFinally 取消 先交差再摘牌 → 崩溃后无人知晓；续租不停 → TTL 保护网失效，永久死锁
INV-5 消息先落库、后 XADD；事件日志异步且失败不影响 turn 反序 → 用户看到了、刷新后消失；日志同步写 → 冷存储抖动拖垮在线链路
INV-6 outbox 只能裁剪 turn 已结束的部分（turnStartId 保护） 长 turn 前半段被裁 → 该 turn 内的续传出现空洞
INV-7 middleware / adapter 中的阻塞调用必须 subscribeOn(boundedElastic) 占死事件循环线程，全 pod 所有 session 一起卡；症状是吞吐莫名掉到个位数
INV-8 事件管道一律 concatMap；只有 ready 队列消费用 flatMap 批次乱序写入。小批量时看不出，批稍大就错位
INV-9 所有 Redis key 带 {s<N>} hash tag，分片数 256 永不修改 Cluster 下 Lua 报 CROSSSLOT；改分片数等于数据迁移
INV-10 msgSeq 每 session 独立且单调无洞（不用全局自增） 客户端的空窗判定失效 → 要么永远误判要么永远漏判
INV-11 ctrl 水位 ctrlId 必须与 XADD 在同一 Lua 脚本内产生 快照与流位置错开 → 重放旧帧覆盖新状态 → 状态翻转
INV-12 ctrl-stream 只用非阻塞 XREAD 轮询，禁止 XREAD BLOCK（轮询粒度随意） 阻塞命令独占连接 → Redis 连接数随 SSE 连接数线性放大，几千即打满

注 · 工具内部的阻塞调用不需要手动 offload——ToolExecutor 已默认 subscribeOn(Schedulers.boundedElastic())。INV-7 只针对 middleware 和 adapter。

G

已经定下的技术决策

这些已经收敛，不需要重新论证。

议题选择理由
Redis 最低版本6.2MINID 按时间裁剪与 XAUTOCLAIM 都是 6.2；7.0 只有分片 pub/sub 需要，用不到
原子性实现Lua 脚本精确、无浪费。启动 SCRIPT LOAD + 运行期 EVALSHA，testcontainers 写单测
键命名{s<N>} hash tag，256 分片Cluster 下 Lua 必须同槽；同时解决热点分布
ready 队列结构单个全局 Stream + 消费组每 pod 只监听一条 stream、只占一条阻塞连接
ready 是否分片否（session key 仍 256 分片）分片只为让摘牌脚本同槽；ready 分片会让每 pod 监听 N 条 stream
投递原子性放弃，靠客户端重试单个 ready 与分片 inbox 必然不同槽；重试约定写进协议文档
排他性来源lease，非读取排他多个 pod 读到同一 sid 是预期行为，代价只是两次 SET NX
消息真相源消息表（DB）需要长期重放与分页拉取；outbox 退化为实时推送与短期续传的缓存
SSE 的 idper-session msgSeq，无洞一个 id 空间覆盖 Stream 与 DB 两个数据源
断线重连（消息）全量重放，客户端去重服务端不做位置定位；首次加载与空窗恢复统一为一条路径
控制通道快照 + 水位 + 流重放保证瞬时信号不被轮询窗口漏掉；水位与 XADD 原子产生以防翻转
跨节点中断复用 inbox，不开 pub/sub200ms 足够（中断本就在下一个推理迭代边界生效）；少一条与 lease 绑定的订阅生命周期
outbox 保留5–10 分钟全量重放的成本与窗口成正比；长期历史由消息表兜底
outbox 读取不用 consumer group扇出语义。用了之后多端登录的两个设备各拿一半事件
指令队列消息与控制统一进 inbox一套顺序、一套持久化、一套故障恢复；靠两个游标区分消费时机
富消息来源表达型工具的入参函数调用是模型受训行为，schema 即契约；不需要解析自由文本或强制 JSON 输出
卡片内容冻结落库重开会话所见即当时所见；代价是需在 UI 标注数据时间
合批窗口80ms约 12 次/秒仍然流畅；主要收益是信封开销摊薄与客户端渲染压力，不是 Redis QPS
Redis 客户端Lettuce reactive 全线统一Jedis 阻塞；outbox 写入在热路径上，每 80ms 一次 × 每个在飞 turn
线程模型不建 worker 线程池控制的是并发度不是线程数；turn 绝大部分时间在等网络
全局 LLM 限流先不做429 处理无论如何都要写；B 已是粗粒度上限；用 429 率反馈到 A 自适应收紧
H

明确不做的事

列出来是为了避免有人"补全"它们。

沙箱（Docker / K8s / E2B 等） 本期不含不可信代码执行。省掉 SandboxSnapshotSpec / SandboxExecutionGuard 与大对象存储整条链路。
多租户隔离 企业内部系统，userId 即员工 id。准入层不做租户配额。
为跨节点中断单开 pub/sub 通道 inbox + 200ms 轮询已覆盖。少一个 key、少一条与 lease 绑定的订阅（本身就是泄漏风险）、少一处集群 pub/sub 广播问题。
服务端的 SSE 续传定位（按 Last-Event-ID 跳帧） 改为全量重放 + 客户端去重。服务端不保存也不解析客户端位置。
从 AgentState 重建客户端消息 消息已单独存储，render() 只在生成时跑一次，不存在双路径不一致。
Agent Factory / Session Factory / Cache / Processer pool v2 的 agent 是无状态引擎，单例服务所有 (userId, sessionId)，state 按需从 store 加载。整层抽象是零代码。
Agent 内部的 inbox / outbox / Event Bus 与 Session 层重复。且 event bus 会丢掉背压——慢客户端不再传导回读取端，直接 OOM。
自研 Interceptor 六钩子 用 v2 的 Middleware。自研要重新实现异常传播、短路、排序，而且内置能力全是 middleware，自研就用不上。
Message router / Connection Manager 的跨节点路由 Redis Stream 扇出替代。SSE 连任意节点都能拿到全部数据，多端登录不需要任何特殊处理。
Session Manager "谁拥有 session"这个问题在 lease 模型下消失了。生命周期就是几个 key 的 TTL。
工具直接写 outbox 会与合批管道形成两个写入者，卡片和文本的交错顺序间歇性错乱——最难查的那种 bug。
让模型直接输出客户端消息格式 JSON 流式体验丧失、文本质量下降、转义地狱、改协议要改 prompt。走工具调用全部绕开。
估算合计 ≈ 14–15 人周 关键路径 P0 → P1 → P3 最高风险 P3 阻塞项：云 Redis 的 Lua 支持
