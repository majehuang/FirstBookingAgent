# P1 接口与投递测试用例

## 共享前置条件

- 应用以单节点模式启动，连接隔离的 Redis 7.0 和 PostgreSQL。
- 会话 `s-p1` 归属于已认证用户 `u-p1`。
- POST 请求体采用协议 v1.1 `UserInstruction`；本文件主要使用 `MESSAGE + QUEUED`。
- 可通过 Redis 命令代理或故障注入器分别令第一次、第二次 `XADD` 失败。

## HTTP 接口

### API-001　有效消息立即返回 202

- 优先级：P0；层级：接口集成。
- 步骤：让可控 Agent 在开始后阻塞 5 秒；POST 一条合法消息并计时。
- 预期：HTTP `202`；响应包含原 `instructionId`、非空 `replyId`、正数 `msgSeq`；响应在 Agent 完成前返回，不能等待完整回复。

### API-002　用户自己的消息由服务端落库并进流

- 优先级：P0；层级：端到端。
- 步骤：POST 合法消息，随后读取消息表和 SSE。
- 预期：数据库和 SSE 都出现同一条 `role=USER,type=TEXT` 消息；其 `msgSeq` 等于 Ack；客户端无需本地回显。

### API-003　未认证请求被拒绝

- 优先级：P0；层级：接口契约。
- 步骤：分别使用缺失、无效和过期凭据调用接口。
- 预期：按正式鉴权契约返回 `401` 或 `403`；Redis、消息表和 Agent 均无副作用。

### API-004　用户不能向他人的会话投递

- 优先级：P0；层级：安全集成。
- 步骤：使用 `u-other` 的有效凭据向 `u-p1/s-p1` 投递。
- 预期：请求被拒绝；响应不泄露会话是否存在；无 Redis、数据库或 Agent 副作用。

### API-005　必填字段和枚举校验

- 优先级：P0；层级：参数化接口测试。
- 数据：缺失/空白 `instructionId`，缺失 `kind`、`priority`、`createdAt`，`MESSAGE` 缺失/空白 `text`，未知枚举，畸形 JSON。
- 预期：返回契约定义的 `4xx`；不写 inbox、ready 或消息表。

### API-006　文本长度边界

- 优先级：P1；层级：参数化接口测试。
- 步骤：分别提交 32768 和 32769 个字符的文本。
- 预期：32768 字符正常接受；32769 字符返回 `4xx` 且无副作用。

### API-007　路径中的 sessionId 校验

- 优先级：P1；层级：参数化接口测试。
- 数据：空白、超过 128 字符、含空白或 `{`、`}`、`:` 的 sessionId，以及合法中文 sessionId。
- 预期：非法值返回 `4xx` 且不能进入 Redis key；合法值可投递。

### API-008　同会话相同 instructionId 幂等重试

- 优先级：P0；层级：Redis + PostgreSQL 集成。
- 步骤：并发或顺序提交两次完全相同请求。
- 预期：两次都获得同一 `replyId`、同一 `msgSeq`；消息表只有一条 USER 消息；只启动一个 turn；序号不被重复请求烧掉。

### API-009　不同会话的相同 instructionId 互不冲突

- 优先级：P1；层级：集成。
- 步骤：向两个属于同一用户的不同 session 投递相同 `instructionId`。
- 预期：两次都成功并各自产生独立 `replyId/msgSeq`；两个 session 均启动一次 turn。

## inbox → ready 投递

### DLV-001　成功路径严格先写 inbox 后写 ready

- 优先级：P0；层级：Redis 集成。
- 步骤：记录 Lettuce 命令调用或 Redis MONITOR 测试代理中的两次写入。
- 预期：第一次 `XADD` 的 key 为 `KeyNamespace.inbox(sid)`，第二次为 `KeyNamespace.READY`；顺序不可反转；两次成功后才产生 Ack。

### DLV-002　inbox 写入失败时不写 ready

- 优先级：P0；层级：故障注入。
- 步骤：令第一次 `XADD` 失败。
- 预期：返回 `5xx`，没有 Ack；ready 无新令牌；数据库不产生已接受的 USER 消息；Agent 不启动。

### DLV-003　ready 写入失败时不返回 202

- 优先级：P0；层级：故障注入。
- 步骤：允许 inbox 写入，令 ready 的 `XADD` 失败。
- 预期：返回 `5xx`，没有 Ack；inbox 中允许保留指令；Agent 尚未启动。

### DLV-004　第二步失败后使用同一 instructionId 重试可恢复

- 优先级：P0；层级：故障注入集成。
- 前置：先执行 `DLV-003`，随后恢复 Redis。
- 步骤：用完全相同的 `instructionId` 再次 POST。
- 预期：最终返回 `202`；ready 获得有效唤醒；只落一条 USER 消息、只执行一个 turn、`msgSeq` 无洞。

### DLV-005　inbox 保留完整指令语义

- 优先级：P1；层级：Redis 契约。
- 步骤：投递包含 Unicode、换行和最大合法长度文本的指令并读取 Stream。
- 预期：反序列化后 `instructionId/kind/priority/text/createdAt` 与请求一致，不出现字符损坏或时间精度意外丢失。

### DLV-006　ready 令牌可定位正确 session

- 优先级：P0；层级：Redis 契约。
- 步骤：交错向两个 session 各投递一条消息并读取 ready。
- 预期：每个成功请求产生可解析的唤醒令牌，令牌准确指向对应 session；不会使用错误分片的 inbox。

### DLV-007　提交期间 Agent 忙碌不阻塞 POST

- 优先级：P1；层级：集成。
- 步骤：让同一 session 的第一轮长期运行，再提交第二条 QUEUED 消息。
- 预期：通信层仍完成 inbox→ready 并及时返回 `202`；第二条消息排队，不能在 HTTP 层同步等待第一轮结束。
