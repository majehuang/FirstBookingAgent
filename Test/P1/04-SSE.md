# P1 SSE 测试用例

## 连接与线格式

### SSE-001　建立消息事件流

- 优先级：P0；层级：HTTP 集成。
- 步骤：以合法用户调用 `GET /sessions/{sid}/events`。
- 预期：返回 `200`，`Content-Type` 为 `text/event-stream`，连接保持打开并能接收后续事件。

### SSE-002　SSE id 等于 ClientMessage.msgSeq

- 优先级：P0；层级：契约集成。
- 步骤：让 outbox 中存在 `msgSeq=41,42` 两条消息并建连。
- 预期：两帧 SSE 的 `id` 分别严格为 `41`、`42`；`data` 可反序列化为对应 `ClientMessage`。

### SSE-003　未认证或越权连接被拒绝

- 优先级：P0；层级：安全集成。
- 步骤：分别使用无凭据、无效凭据和其他用户凭据连接。
- 预期：按鉴权契约拒绝；不泄露会话数据，也不创建 Redis 读取循环。

## 全量窗口重放

### SSE-004　建连从 outbox 当前窗口起点全量重放

- 优先级：P0；层级：Redis + HTTP 集成。
- 步骤：预置同 session 的 5 条 outbox 消息后建连。
- 预期：客户端依序收到全部 5 条，而不是只收到最新一条或从某个服务端游标续传。

### SSE-005　不解析 Last-Event-ID

- 优先级：P0；层级：契约集成。
- 步骤：分别不带 Header、带 `Last-Event-ID: 3`、带非法值建连。
- 预期：三次都按相同窗口起点全量重放；非法值不会引发位置解析错误。

### SSE-006　不解析查询位置参数

- 优先级：P0；层级：契约集成。
- 步骤：分别携带 `since=3`、`cursor=...` 和未知查询参数建连。
- 预期：位置参数不改变重放起点；具体是忽略还是按统一未知参数策略拒绝，必须与正式接口文档一致，但绝不能做服务端断点续传。

### SSE-007　重放与实时切换期间不漏消息

- 优先级：P0；层级：并发集成。
- 步骤：在服务端重放最后一条历史帧的同时向 outbox 追加新帧，重复执行至少 100 次。
- 预期：新帧最终一定被连接收到；按 `msgSeq` 排序后没有缺失。若边界允许重复，重复只能由全量重放语义产生且可被客户端规则丢弃。

## 扇出、隔离与生命周期

### SSE-008　两个客户端都收到完整消息流

- 优先级：P0；层级：集成。
- 步骤：为同一 session 同时建立两个 SSE 连接，然后生成一轮回复。
- 预期：两个连接各自收到完整且相同的消息序列；outbox 不能使用会让客户端分摊消息的消费组语义。

### SSE-009　不同 session 严格隔离

- 优先级：P0；层级：集成。
- 步骤：连接 session A 和 B，交错生成消息。
- 预期：A 只收到 A 的 outbox，B 只收到 B 的 outbox；`msgSeq` 在各 session 内独立。

### SSE-010　断开连接后释放订阅资源

- 优先级：P1；层级：资源集成。
- 步骤：循环建立并主动关闭 SSE 连接，等待一个短的收敛周期。
- 预期：对应订阅、定时轮询和连接对象被取消；活跃订阅数回到基线；不存在持续读取或明显线程泄漏。

### SSE-011　慢客户端不改变持久化顺序

- 优先级：P1；层级：背压集成。
- 步骤：建立一个正常客户端和一个故意慢读客户端，快速生成多条消息。
- 预期：消息表和 outbox 写入不被慢客户端乱序；正常客户端持续接收；慢客户端的处理策略符合已配置的缓冲/断开规则且不影响其他连接。

## P1 验收边界

P1 的“刷新页面能续上”只要求刷新发生在 outbox 窗口内并通过全量重放恢复。
离线超过窗口后的数据库历史补齐、客户端三规则完整验收和 turn 中裁剪保护属于 P4。
