# P2 功能验证报告（2026-08-25）

## 结论

**P2 主体代码已落地，但按 `Test/P2` 的 78 条用例验收，G2 当前不通过。**

| 状态 | 数量 | 含义 |
|---|---:|---|
| PASS | 41 | 自动化测试或本次复现证明预期成立 |
| PARTIAL | 14 | 主路径成立，但缺故障、压力、线格式或完整链路证明 |
| FAIL | 14 | 当前实现与测试预期直接冲突 |
| NOT RUN | 9 | 缺少 P2 脚本化 Agent、真实模型或并发夹具 |
| 合计 | 78 | 与 P2 用例总数一致 |

G2 的主要阻断项：

1. payload 只做浅复制，嵌套 `items` 和 item Map 没有深冻结。
2. `ClientCapabilities.degrade()` 没接入真实出站链路，仅文本客户端不会自动收到服务端降级消息。
3. 缺少 PostgreSQL + Redis + Fake 酒店源的 P2 E2E 剧本。
4. loopback 当前顺序是“卡片 → 推荐理由与追问”，不是“推荐理由 → 卡片 → 追问”。
5. `jsonb` 与 `Map.copyOf` 都不保证对象键顺序，重开 CARD 无法保证线格式逐字节一致。


# 修复记录（2026-08-25）

按本报告「修复优先级」逐条处理。**五条 P0 全部完成**，两条 P1 一条完成、一条给出理由暂缓。

## P0-1　递归深冻结　✅

**根因**：`Map.copyOf` 只冻顶层，嵌套 `items` List 与每个 item Map 仍是外部引用；
且它不保证迭代顺序。

**修复**：新增 `Immutables.freeze()` —— 递归冻结并按键排序，用于
`ClientMessage` / `MessageDraft` / `PendingMessage` 三处。
排序而非保留插入序，是因为插入序活不过 `jsonb`。

**验证**：`ImmutablesTest` 9 条，覆盖 REN-002、REN-003、REN-007，
含「改原始集合不影响已冻结内容」与「序列化 100 次逐字节一致」。

## P0-2　确定性线格式　✅

**根因**：`jsonb` 按自己的规则重排对象键，实测 `title → items → dataAsOf`
读回变成 `items → title → dataAsOf`。

**修复**：`Json` 打开 `ORDER_MAP_ENTRIES_BY_KEYS`。首次出站与数据库重建后
都按键排序，两边才可能对上。**不需要让首次出站也从库里重建**。

**验证**：`PostgresMessageRepositoryIntegrationTest.卡片经数据库往返后线格式不变`（FRZ-011），
真库、嵌套两层、故意用非字典序插入。

## P0-3　能力降级接入真实出站　✅

**根因**：`ClientCapabilities.degrade()` 没有任何调用方。

**修复**：出站有<b>两条</b>路径，两条都要覆盖 —— 这一点最初漏了，
实测「仅文本客户端重开会话仍收到 CARD」才发现：

| 路径 | 落点 |
|---|---|
| 消息流 | `RedisMessageSubscriber.messages()` |
| 历史拉取 | `RedisBackend.since()` |

降级放在**读取侧**：outbox 里必须存完整卡片，否则能力不同的两个客户端
只能看同一份被削过的内容，新客户端升级后也拿不回历史里的富消息。

CLI 增加 `--capabilities FULL|TEXT`。

**验证**：`CapabilityDegradationIntegrationTest` 4 条（真 Redis，UI-006）+ 实机双路径复现。

## P0-4　P2 脚本化 E2E Agent　✅

**修复**：

- `ScriptedTurnEngine` 增加 `!card` 剧本：**推荐理由 → 工具调用 → 工具结果 → 追问 → 终止**。
  伪造的只是调用与结果，**渲染走真实注册表** —— 否则端到端验的是另一套代码
- `--engine scripted` 现在也带渲染器
- loopback 的 `hotelScript` 顺序改为 **推荐理由 → 卡片 → 追问**（原为卡片在前）

**验证**：`ScriptedTurnEngineTest` 增 3 条断言顺序与状态行抑制；
`ScriptedReplyTest` 断言 loopback 六步顺序。实机 `!card` 走 Redis 全链路，
输出顺序与规格一致，重开逐字节一致。

## P0-5　卡片入参策略　✅

**修复**：新增 `CardRequest`，工具与 middleware **共用同一份判断**：

| 输入 | 策略 | 为什么不静默处理 |
|---|---|---|
| 空列表 | 结构化错误 | 空卡片是个空框，而模型以为已经展示过了 |
| 超上限（>5） | 结构化错误，**不截断** | 截断会让 `shown` 与用户实际看到的对不上 |
| 重复 id | 去重保留首次 | 通常是模型的小失误，去重比打回省一轮交互 |
| id 全查不到 | 结构化错误 | 同空卡片 |

入参不合法时 middleware **不进补全服务**。

**验证**：`HotelToolsTest` 增 6 条（TOOL-004、TOOL-005）。

> ⚠️ **TOOL-001 仍为 PARTIAL**：`@ToolParam` 表达不了数组上限，
> Schema 里没有 `maxItems`。上限写在描述里提示模型，由 `CardRequest` 兜住。

## P1-6　middleware 契约与规划统一　✅

**结论：修规划，不修实现。**

`withMetadataEntry` 是 `AgentEvent` 上的方法，而补全结果要送到的是**工具**，
工具读的是 `ToolUseBlock` —— 两者之间没有通路。规划原文写的路走不通。

已在 `开发规划.md` E §P2 加修订块，记录实际做法与那个签名上看不出来的坑
（`content` 才是校验与绑定的来源）。

**验证**：`HotelToolsTest` 增 2 条断言 MID-004 的实质契约 ——
返回新对象、原对象不变、已有 metadata 不丢失、`content` 与 `input` 同步重建。

## P1-7　Transcript per-reply reducer　⏸ 暂缓

**未做。**报告本身把它列为 P1 并注明「若未来允许交错 reply」。

当前 P1 架构下**同一 session 同时只有一个 worker 持牌**（INV-3），
reply 不会交错。现有实现在 blockId 变化时 flush，文本不会串扰，
只是不会把两个 reply 各自的片段重新聚合。

**开工条件**：P3 之后若出现同 session 并发 turn，或引入子 agent 并行输出。
届时 ADP-003 / ADP-010 才有真实场景。
