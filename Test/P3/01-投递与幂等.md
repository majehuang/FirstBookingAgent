# P3 投递终态与幂等测试用例

## inbox → ready 顺序与故障终态

### DLV-001　成功投递严格先写 inbox 再写 ready

- 优先级：P0；层级：Redis 集成；覆盖 INV-1。
- 步骤：通过命令代理记录一次投递的 Redis 命令、key 和 Stream ID。
- 预期：先成功 `XADD inbox`，后执行 `XADD ready`；两步成功后才产生成功回执。

### DLV-002　inbox 写入失败时不写 ready

- 优先级：P0；层级：故障注入。
- 步骤：让第一条 `XADD inbox` 超时或返回错误。
- 预期：不执行 ready 写入；接口返回 5xx；数据库、inbox、ready 均没有伪成功状态。

### DLV-003　ready 写入失败时保留 inbox 并返回失败

- 优先级：P0；层级：故障注入。
- 步骤：inbox 写入成功后让 `XADD ready` 失败。
- 预期：不返回 202；inbox 条目保留，客户端可使用同一 instructionId 重试；不能回滚或删除已写 inbox。

### DLV-004　两条命令都成功才返回 202

- 优先级：P0；层级：接口契约。
- 数据：两步成功、第一步失败、第二步失败、调用方取消。
- 预期：仅两步都成功返回 202；失败响应不携带会误导客户端等待的伪 replyId/msgSeq。

### DLV-005　ready 失败后的同 instructionId 重试只执行一轮

- 优先级：P0；层级：Redis + PostgreSQL 集成。
- 步骤：制造“inbox 成功、ready 失败”，随后用相同 instructionId 重试并恢复 ready。
- 预期：允许 inbox 存在重复投递痕迹，但消息表只有一条 USER，Agent 只启动一轮，回复只生成一次。

### DLV-006　并发重试同一 instructionId 不重复回复

- 优先级：P0；层级：多 pod 并发。
- 步骤：让 20 个客户端/线程同时用相同 instructionId 重试，两个 pod 竞争处理。
- 预期：数据库唯一约束与 turn claim 只放行一轮；msgSeq 无洞；所有成功回执引用同一原始 reply。

### DLV-007　崩溃在 inbox 与 ready 之间后可由重试恢复

- 优先级：P0；层级：进程故障注入。
- 步骤：在 inbox XADD 成功后硬杀 ingress，再用相同 instructionId 重试。
- 预期：session 最终被唤醒并处理；不丢消息、不重复回复、不依赖人工扫描 Redis。

### DLV-008　重试契约写入正式协议文档

- 优先级：P1；层级：文档契约。
- 预期：文档明确“未收到 202/超时/5xx 时使用同一 instructionId 重试”；说明第二步失败时 inbox 可能已写入，客户端不得生成新 id 重试。
