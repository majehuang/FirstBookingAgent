# P3 消费组、Consumer 生命周期与心跳测试用例

## 消费组初始化与 consumer 命名

### GRP-001　启动时创建 ready/workers 消费组

- 优先级：P0；层级：Redis 集成。
- 步骤：在空 Redis 启动 pod。
- 预期：执行等价于 `XGROUP CREATE ready workers 0 MKSTREAM`；Stream 和 group 均存在，起始位置为 0 而非 `$`。

### GRP-002　并发初始化吞掉 BUSYGROUP

- 优先级：P0；层级：多 pod 并发。
- 步骤：10 个 pod 同时对同一 ready 初始化 group。
- 预期：恰有一个创建成功，其余只忽略 BUSYGROUP；其他 Redis 错误必须传播，不能全部吞掉。

### GRP-003　重启初始化不改变已有 PEL 和 last-delivered-id

- 优先级：P0；层级：Redis 集成。
- 步骤：制造 pending 条目后重启 pod 并再次初始化。
- 预期：group 不被重建，PEL、消费者归属和投递水位保持原值。

### GRP-004　consumerName 等于 pod 名

- 优先级：P0；层级：配置契约。
- 预期：XREADGROUP/XCLAIM 使用部署系统提供的稳定 podName；空值、空白和超长名称启动失败并给出明确错误。

### GRP-005　consumerName 不追加时间戳或随机后缀

- 优先级：P0；层级：快照/架构测试。
- 步骤：同一 pod 配置连续创建 registry/dispatcher。
- 预期：consumerName 完全相同，不含启动时间、UUID、线程号，避免重启后死 consumer 元数据无限增长。

### GRP-006　不同存活 pod 使用不同 consumerName

- 优先级：P0；层级：部署集成。
- 步骤：启动 pod-a、pod-b 并各认领令牌。
- 预期：XINFO CONSUMERS 显示两个 consumer；令牌归属可追踪，不共享同一 consumer 身份。

### GRP-007　同名 pod 重启可接续原 consumer 元数据

- 优先级：P1；层级：重启集成。
- 步骤：pod-a 留下 PEL 后退出，再以 pod-a 名重启。
- 预期：不创建带后缀的新 consumer；原 PEL 可由启动回收流程处理，元数据数量不增长。

## 持牌期 PEL 心跳

### HBT-001　PEL 心跳与 lease 续租同频

- 优先级：P0；层级：虚拟时间。
- 步骤：运行长 turn，推进 10 秒周期。
- 预期：每次 lease 续租同时对当前 ready token 执行一次 PEL 心跳；两者不会长期漂移。

### HBT-002　心跳使用 XCLAIM JUSTID

- 优先级：P0；层级：命令契约；覆盖 INV-2c。
- 预期：命令语义为 `XCLAIM ready workers <consumer> 0 <tokenId> JUSTID`；MIN-IDLE 为 0，且指定当前 consumer 和令牌 ID。

### HBT-003　心跳重置 idle 且不增加投递计数

- 优先级：P0；层级：真 Redis。
- 步骤：记录 XPENDING 的 idle 与 deliveries，执行多次 JUSTID 心跳。
- 预期：idle 周期性归零；delivery count 不因心跳增加，避免错误触发重试告警。

### HBT-004　长 turn 有心跳时不会被 XAUTOCLAIM

- 优先级：P0；层级：多 pod Redis 集成。
- 步骤：turn 时长超过 MIN-IDLE，pod-a 持续心跳，pod-b 周期回收。
- 预期：token 始终归 pod-a；pod-b 不重复启动同一 session，不产生 lease churn。

### HBT-005　只为本 Worker 当前 pending 令牌心跳

- 优先级：P0；层级：隔离测试。
- 步骤：同一 pod 并发多个 session，并混入其他 consumer 的 pending token。
- 预期：每个 Worker 只刷新自己的 token；不接管、不刷新其他 consumer 或已完成 token。

### HBT-006　turn 结束后停止 PEL 心跳

- 优先级：P0；层级：生命周期。
- 数据：正常完成、引擎异常、取消、lease lost、pod 优雅停机。
- 预期：终止后无新的 XCLAIM；已 ACK token 不被心跳重新创建 pending 状态。
