# P3 PEL 回收、死 Consumer 清理与 ready 裁剪测试用例

## XAUTOCLAIM 回收

### RCV-001　pod 启动立即执行一次回收

- 优先级：P0；层级：Redis 集成；覆盖 INV-2b。
- 步骤：先制造超过 MIN-IDLE 的 pending token，再启动新 pod。
- 预期：无需等待第一个 30 秒周期即触发 XAUTOCLAIM，并把令牌交给可用 Worker。

### RCV-002　运行期每 30 秒周期回收

- 优先级：P0；层级：虚拟时间/短参数真 Redis。
- 预期：启动回收后按固定周期继续；一次失败被记录并按策略重试，不能让调度任务永久停止。

### RCV-003　MIN-IDLE-TIME 固定为 60000 且不能为 0

- 优先级：P0；层级：配置/命令快照。
- 预期：生产命令使用 60000ms；0、负数或小于冻结下限的配置在启动时拒绝，避免抢走存活 pod。

### RCV-004　未达到 MIN-IDLE 的 token 不被回收

- 优先级：P0；层级：真 Redis。
- 步骤：创建 idle 小于阈值且无心跳的 pending token，另一 pod 执行回收。
- 预期：归属不变，不启动重复 Worker。

### RCV-005　达到 MIN-IDLE 的死 token 被接管

- 优先级：P0；层级：真 Redis。
- 步骤：consumer 退出并让 token idle 达阈值。
- 预期：任一存活 pod 可 claim；随后仍通过 lease 竞争保证一个执行者。

### RCV-006　循环 XAUTOCLAIM 直到游标 0-0

- 优先级：P0；层级：分页集成。
- 步骤：制造超过单批 count 的过期 PEL。
- 预期：使用返回游标继续调用，直至 `0-0`；不能只处理第一页。

### RCV-007　多页回收不遗漏不重复

- 优先级：P0；层级：压力集成。
- 步骤：创建至少 1000 个 pending token，混合未过期、已过期和已删除 Stream entry。
- 预期：所有且仅所有可回收 token 被处理一次；deleted IDs 按 Redis 返回语义清理，不导致死循环。

### RCV-008　所有 pod 都可幂等回收且不选主

- 优先级：P0；层级：多 pod 并发。
- 步骤：3 个 pod 同时从相同起始游标运行回收。
- 预期：不需要 leader key；重复 claim 只造成可接受竞争，lease 最终只允许一轮执行，回收任务不会互相删除工作。

### RCV-009　回收后的 token 进入统一 Worker 管道

- 优先级：P0；层级：端到端。
- 预期：回收 token 与正常 XREADGROUP token 走相同 lease、drain、unlease、XACK 管道，不存在跳过 lease 的特殊执行分支。

### RCV-010　关闭回收时 PEL 会永久滞留

- 优先级：P0；层级：反证测试；INV-2b 专属。
- 步骤：制造死 consumer pending，禁用回收并运行超过多个扫描周期。
- 预期：令牌仍在 PEL 且不会自动回队；启用回收后才恢复。该用例证明 Redis 不会替系统自动处理 PEL。

## 死 consumer 清理

### CLN-001　仅清理 idle 超过 1 小时且 pending=0 的 consumer

- 优先级：P0；层级：真 Redis；覆盖 INV-2d。
- 步骤：准备 idle/pending 组合矩阵并运行清理。
- 预期：只对同时满足两条件的 consumer 执行 DELCONSUMER。

### CLN-002　idle 边界值不会提前清理

- 优先级：P0；层级：边界测试。
- 数据：阈值前 1ms、恰好阈值、阈值后 1ms。
- 预期：按冻结的严格 `>` 语义处理，边界不会因秒/毫秒换算被提前删除。

### CLN-003　pending 大于 0 时绝不 DELCONSUMER

- 优先级：P0；层级：安全测试。
- 步骤：consumer idle 很久但仍有一条 pending。
- 预期：保留 consumer 和 pending；记录等待回收原因，不把 pending=0 当性能优化省略。

### CLN-004　执行顺序固定为先回收后清理

- 优先级：P0；层级：调用顺序。
- 步骤：同一维护周期同时存在可回收 PEL 与可清理 consumer。
- 预期：完整 XAUTOCLAIM 游标循环结束后才 XINFO/DELCONSUMER；异常中断时宁可不清理。

### CLN-005　有 pending 时 DELCONSUMER 会让工作消失

- 优先级：P0；层级：真 Redis 反证；INV-2d 专属。
- 步骤：在隔离 group 故意删除 pending>0 的 consumer。
- 预期：记录 Redis 返回的丢弃 pending 数，令牌不再可由正常 PEL 回收；证明生产守卫不可删除。

### CLN-006　安全清理后 consumer 元数据消失

- 优先级：P1；层级：Redis 集成。
- 步骤：清理 pending=0 的过期 consumer，再查 XINFO CONSUMERS。
- 预期：目标消失，其他 consumer、group 水位和 Stream 数据不变。

### CLN-007　存活 consumer 不因时钟抖动被清理

- 优先级：P1；层级：并发集成。
- 步骤：consumer 正常心跳/取任务，同时维护任务读取 XINFO。
- 预期：活跃 consumer 始终保留；一次 Redis 延迟不能被误解为 idle 超阈值。

## ready Stream 裁剪

### TRM-001　ready 写入使用 MAXLEN 约 100000

- 优先级：P0；层级：命令/配置快照。
- 预期：写入带近似 `MAXLEN ~ 100000` 或等价集中配置；值不能散落为多个字面量。

### TRM-002　阈值以下不主动裁剪

- 优先级：P1；层级：Redis 集成。
- 步骤：写入少于阈值的 ready token。
- 预期：条目均可由消费组读取；近似裁剪不能被错误实现为每次全量重建 Stream。

### TRM-003　积压场景裁剪后新工作仍可消费

- 优先级：P1；层级：容量集成。
- 步骤：使用缩小的测试阈值制造大量已完成历史和新 token。
- 预期：新 token 可读；已完成历史允许裁剪；group 不被删除或重建。

### TRM-004　XTRIM 不保护 PEL 的风险反证

- 优先级：P0；层级：真 Redis 反证；覆盖 INV-2b。
- 步骤：制造 pending token 后故意把 Stream 裁到其 ID 之后，再观察 XAUTOCLAIM deleted IDs。
- 预期：证明裁剪可能移除 PEL 对应实体；生产阈值与监控必须避免积压触达危险区。

### TRM-005　裁剪安全说明与告警存在

- 优先级：P1；层级：文档/配置检查。
- 预期：配置处说明“XTRIM 不看 PEL”；至少暴露 ready 长度、PEL 深度和最老 idle，接近阈值时可告警。
