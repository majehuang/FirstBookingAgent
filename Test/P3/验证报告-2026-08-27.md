# P3 多节点正确性验证报告

## 1. 结论

**最终结论：P3a 核心机制大部分可运行，但 P3 整体与 G3 均不通过。**

> **2026-08-28 决议更新**：本报告原先将 P3-13 的 AgentState CAS 视为契约阻断，现已取消该判断。
> AgentStateStore 只需共享 PostgreSQL 持久化并允许 LWW；防双跑唯一由 lease（INV-3）保证，
> 不要求版本/CAS 或冲突重试。此修订不改变本报告因原 turn 丢失及 P3b 未执行而判定 G3 不通过的结论。

主要原因不是构建失败，而是验收语义仍未满足：

1. Java 21 下的两次完整验证中，`MultiWorkerIntegrationTest` 都出现 **2 个 session 的原始 turn 夭折**。
2. PostgreSQL 对账确认这些 USER 消息已经设置 `turn_claimed_at`，但同 `replyId` 没有任何 ASSISTANT 输出。
3. 测试用全新的 `i-resend-*` 指令恢复了会话，却没有恢复原 `instructionId`；这与正式客户端协议“收到 202 后节点故障由服务端接管，客户端不要重试”冲突。
4. P3b 的随机 kill、Redis 抖动、长 GC、网络分区、100 session 长跑、100 次硬杀时延采样均未执行。

因此，`mvn clean verify` 的绿色结果只能证明现有自动化断言通过，**不能作为 G3 放行依据**。

## 5. P0 阻塞：原始 turn 夭折后不可恢复

### 5.1 复现结果

`MultiWorkerIntegrationTest` 的第一项使用 3 个 worker、12 个 session、每个 session 3 轮，共 36 个原始 turn。

两次完整验证结果一致：

| 运行 | 原始 turn | 正常产生回复 | 夭折 | 测试报告结果 |
|---|---:|---:|---:|---|
| 第一次 | 36 | 34 | 2 | PASS |
| Java 21 重跑 | 36 | 34 | 2 | PASS |

两次运行都输出：

```text
有 2 个 session 存在夭折的轮次，按承诺它们应当能靠重发恢复
```

### 5.2 数据库证据

两次运行累计发现 4 条满足以下条件的 USER 消息：

```text
turn_claimed_at IS NOT NULL
AND 不存在同 session_id、reply_id 的 ASSISTANT 消息
```

受影响 session 每个最终都是：

```text
USER = 4
ASSISTANT reply = 3
```

其中前三条 USER 是原始测试指令，第四条是测试后来创建的 `i-resend-*` 新指令。新指令让会话恢复可用，但原来的 USER 仍然没有回复。

### 5.3 为什么相同 instructionId 无法恢复

`claimTurn` 只允许 `turn_claimed_at IS NULL` 的记录再次认领：

```sql
UPDATE agent_message SET turn_claimed_at = now()
 WHERE session_id = ?
   AND instruction_id = ?
   AND turn_claimed_at IS NULL
```

原 turn 已经认领过，所以即使重新投递相同 `instructionId`，`claimTurn` 也会返回 false，Worker 会直接跳过。当前测试实际使用的是新的 `instructionId`：

```java
deliver(session, "i-resend-" + UUID.randomUUID(), "重发");
```

这只能证明“用户再问一个新问题时 session 还能工作”，不能证明原指令被服务端接管恢复。

### 5.4 契约冲突

正式客户端协议规定：

- 收到 202 后，执行节点故障由其他节点在 90 秒内接管。
- 客户端不需要重试，也不应提示用户重新发送。

当前行为则是：原 turn 可能永久没有回复，必须由用户创建一条新逻辑指令才能继续。因此本次结果违反：

- G3“无消息丢失”。
- CHA-005/CHA-010“每个 instructionId 最终恰有一个有效回复”。
- 客户端协议中的执行节点故障恢复承诺。

## 8. 测试与文档问题

### 8.1 多 Worker 测试放宽了 G3 断言

`assertNoDuplicatesAndNoLoss()` 对助手回复只断言：

```text
assistant replies <= expected turns
```

没有断言等于期望值，所以 0 个回复也可能通过该断言。随后 `assertResendAlwaysWorks()` 使用新 instructionId 掩盖原 turn 丢失。该测试应先对正式契约达成一致，再决定是：

- 修复服务端，使已认领但未完成的 turn 可安全重跑；或
- 明确修改客户端协议与 G3，承认用户必须发送一条新指令恢复。

在当前冻结协议下，应采用前者。

### 8.2 P3 测试文档的 SLA 描述已过期

`Test/P3/README.md` 与 CHA-011 仍把 60 秒 MIN-IDLE 和 30 秒 SLA 写成待解决冲突；当前正式规划和客户端协议已于 2026-08-26 决议改为 90 秒。测试文档需要同步，否则验收人员会使用不同门槛。

### 8.3 覆盖率门禁不能代表核心编排路径覆盖

当前 JaCoCo 排除了多个 P3 核心类或整包，包括：

- `LeaseGuard`、`Cursors`、`PelHeartbeat`。
- `ReadyDispatcher`。
- `task/worker/**`。
- `comm/**`。
- `OutboxWriter`。

这些行为有集成测试覆盖，但“JaCoCo 全绿”本身不能证明这些核心路径达到 80%。报告应同时引用行为测试结果，不能只引用覆盖率百分比。

## 9. 放行建议

G3 放行前至少需要：

1. 修复“已 claim 但无回复”的 turn 恢复语义，并增加使用**同一原 instructionId**的接管测试。
2. 把多 Worker 断言改为每个原 instructionId 最终恰有一个有效回复，禁止用新 instructionId 替代原 turn。
3. 完成 CUR-003 与 RCV-007 的缺口。
4. 建立并执行 CHA-005～CHA-012 多进程混沌套件。
5. 同步 Test/P3 的硬杀 SLA 为 90 秒。
6. 重新执行 Java 21 `mvn clean verify` 与数据库一一对账，要求消息丢失数、重复有效回复数、永久卡死 session 数均为 0。

在这些项目关闭之前，建议状态保持：

```text
P3a：PARTIAL PASS
P3b：NOT RUN
G3：FAIL / NOT RELEASED
```
