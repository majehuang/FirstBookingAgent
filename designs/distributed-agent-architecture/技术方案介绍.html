01 / DESIGN PRINCIPLES四条原则锁住系统边界

这套方案的重点不是“把 Agent 部署到多个 pod”，而是把执行权、可见消息、实时推送和模型状态拆成独立、可验证的责任域。

01

Agent 是无状态推理引擎

单例服务所有 (userId, sessionId)；模型上下文由 Store 按需加载，不引入 Agent Factory 或 Session Manager。

02

Redis 是模块契约

通信层与任务层不直接调用、无服务发现、无共享内存；键命名规范就是唯一接口。

03

持久化先于可见

固定顺序为消息表 → outbox → 异步事件日志，避免“用户已看到，刷新后却消失”。

04

租约决定执行权

任意 pod 可读到同一 session，但只有唯一 lease 持有者可以启动 Worker 并写出结果。

核心收益

通信层按 SSE 连接数扩容，任务层按并发 turn 数扩容。两个维度不再互相绑架，生产环境可在不改代码的前提下拆分部署。

02 / SYSTEM ARCHITECTURE整体架构：Redis 契约居中，Agent 边界收敛

03 / DATA RESPONSIBILITY四层存储，各自只做一件事

消息表 · DB
用户可见消息与冻结卡片；历史拉取和超窗重放的真相源。
RETENTION · LONG-TERM
outbox · Stream
同批消息的实时副本；跨 pod 扇出与短期断线重放。
RETENTION · 5–10 MIN
事件日志 · Cold
全量 AgentEvent，用于排查与分析；异步旁路，不阻塞 turn。
RETENTION · COMPLIANCE
AgentState · Redis
模型上下文，由框架管理；与客户端可见消息彻底分离。
RETENTION · SESSION
不可逆的写入顺序

消息表 → outbox → 事件日志（异步）。若 outbox 先写，客户端可能看到一条刷新后不存在的消息；若日志同步写，冷存储抖动会拖垮在线链路。

05 / MESSAGE PIPELINE消息处理流程：从 202 到可恢复的 SSE

06 / CORRECTNESS MODEL正确性机制：租约、回收与水位

机制设计防止的问题关键参数 / 顺序
执行租约SET NX PX，值每次唯一；只允许持有者续租和释放。多 pod 双跑、旧 Worker 误释放新牌。TTL 30s；每 10s 续租。
令牌回收启动一次 + 每 30s 执行 XAUTOCLAIM，循环至 0-0。pod 崩溃后 PEL 永久 pending。MIN-IDLE-TIME 60s，不能为 0。
消费心跳持牌期用 XCLAIM … JUSTID 重置 ready 令牌 idle。长 turn 被误判死亡并频繁回收。与 lease 续租同频。
原子摘牌Lua 同时校验 lease、确认 inbox 已空、删除 lease。释放瞬间新消息进入，导致无人唤醒。抽干 → 摘牌 → XACK。
控制水位Lua 内 XADD ctrl-stream，再把生成的 ctrlId 写回 state。旧控制帧覆盖新快照，产生状态翻转。快照 → 从 ctrlId 开区间重放。
P3 是最高风险阶段

这里的错误通常不会在普通功能测试中出现。验收必须包含随机 kill pod、Redis 抖动、长 GC 与连续对话，并验证无丢失、无重复回复、无 session 永久卡死。

07 / ENGINEERING GUARDRAILS需要写进 Code Review 的不变量

INV-1
投递必须 inbox 先、ready 后；两条成功才返回 202。
INV-2
摘牌与确认 inbox 已空必须在同一 Lua 脚本中完成。
INV-3
lease 值每次抢占唯一；禁止直接使用 pod 名作为值。
INV-4
执行顺序固定：抽干 → 摘牌 → 交差；续租在 doFinally 取消。
INV-5
消息先落库后 XADD；事件日志失败不得影响 turn。
INV-6
outbox 裁剪受 turnStartId 保护，进行中的 turn 不可被截断。
INV-7
middleware / adapter 的阻塞调用必须 offload 到 boundedElastic。
INV-8
AgentEvent 管道一律 concatMap；仅 ready 消费使用 flatMap。
INV-9
所有 session key 带 hash tag，分片数 256 永不修改。
INV-10
msgSeq 按 session 单调无洞，不能使用 DB 全局自增。
INV-11
ctrlId 水位与 XADD 必须在同一 Lua 脚本中原子产生。
INV-12
ctrl-stream 仅允许非阻塞轮询，禁止 XREAD BLOCK。

09 / KEY DECISIONS已经定下的关键技术决策

Redis 形态
阿里云 Redis 7.0 标准版（主从）
满足 XAUTOCLAIM / MINID；企业规模足够，并规避集群 Lua 槽检查。
Redis 客户端
Lettuce Reactive 全线统一
避免热路径阻塞，非阻塞命令可在连接上多路复用。
ready 队列
单个全局 Stream + 消费组
每个 pod 只需一条阻塞连接；session key 仍保留 256 分片。
消息真相源
消息表，而非 outbox 或 AgentState
支撑长期重放、分页与冻结卡片；实时流只承担短期分发。
断线重连
服务端全量重放 + 客户端去重
首次加载与超窗恢复复用同一路径，服务端无需解析位置参数。
跨节点打断
复用 inbox，不增加 pub/sub
统一顺序、持久化与恢复，减少一条与 lease 绑定的订阅生命周期。
富消息
表达型 tool + middleware 成对
schema 即契约，保持文本流式体验，卡片补全后冻结落库。
Workspace 记忆
建议 RemoteFilesystemSpec + Redis BaseStore
多 pod 共享 USER 级长期记忆，避免本地文件系统按 pod 分叉。

把复杂度放在可验证的分布式协议里

Agent 保持单例、无状态、只推理；调度、持久化、扇出、重连与中断都由应用层明确承担。这样既能独立扩容，也能把每一种故障收敛成可复现、可压测、可审查的不变量。
